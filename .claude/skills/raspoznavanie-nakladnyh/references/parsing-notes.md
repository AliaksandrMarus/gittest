# Как устроен разбор накладной и чем лечились ошибки

## Порядок в `recognize.extract(path, tesseract_path)`

1. **pdfplumber**: `extract_text`, `extract_words`, `extract_tables`.
   - Есть таблицы с линиями → `lines_from_table`.
   - Нет таблиц, но есть текст → `lines_from_words(words)`: выгрузки из 1С и «PDF с поиском» часто без линий.
2. **Текста нет** (скан-картинка) → `ocr.ocr_pdf`:
   - страница рендерится через pypdfium2 в 400 dpi, переводится в оттенки серого;
   - выпрямление: `skew_angle` перебирает углы ±2° и выбирает максимум «резкости» горизонтального профиля;
   - `remove_table_lines` стирает длинные горизонтальные и вертикальные линии, пунктир (короткие отрезки с разрывами, склеенные в тонкую полосу) и фоновую сетку (пиксели светлее 185 — в белый). Координаты вертикальных линий сохраняются: это границы колонок;
   - Tesseract `--psm 11` (разреженный текст) с выводом TSV → слова с координатами;
   - `lines_from_words(words, vlines)`.
3. `find_requisites(text, result)` — номер, дата, поставщик.
4. Нет строк → `RecognitionError`, файл уходит в «Ошибки», накладную вводят вручную.

## Шапка и колонки

- `classify_header(label)` → `name, unit, qty, price, amount, rate, vat, total, num, skip`.
  - «Коли-чество», разорванное переносом, — `qty` по «чество».
  - «Количество грузовых мест», «Масса груза», «Примечание» → `skip`: это не количество товара.
  - «№ п/п» → `num`, чтобы номер строки не прилипал к названию.
  - «НОС» = «НДС» (так OCR читает Д); латинские двойники `aceopxyk` переводятся в кириллицу до сравнения.
  - Две колонки «Стоимость» без явной «с НДС»: правая — с НДС (`_fix_kinds`, порядок граф ТТН/ТН).
- Строка шапки ищется по «наимен»/«товар», но не по «ТОВАРНЫЙ РАЗДЕЛ», «товарно-транспортная», «(наименование, адрес)»: это подписи бланка.
- Шапка многострочная: берутся соседние строки без чисел (±3,5 высоты строки).
- Колонки по **вертикальным линиям** (`_groups_from_vlines`) надёжнее, чем по промежуткам между словами: на скане слова соседних граф шапки сливаются. Если по линиям не нашлись `name` и `qty`, используются группы по перекрытию слов (`_column_groups`).

## Строки

- Слова → строки по середине высоты (допуск 0,6 медианной высоты).
- Слово вне колонок левее первой числовой графы считается частью названия: длинное название вылезает за шапку.
- Строка без количества, но с текстом в «Наименовании» — перенос названия, приклеивается к предыдущей.
- «Итого/Всего» — конец таблицы.
- Числа: `parse_number` понимает «1 000,50», неразрывные пробелы и «1.000.50» (точка как разделитель тысяч у OCR). `parse_cell_numbers` различает «1 000» (одно число: после пробела ровно три цифры) и «462.00 92.40» (два числа из слипшихся граф).
- **Слипшиеся графы** (`_split_numeric_cells`): лишнее число из ячейки уходит в следующую пустую графу справа в порядке `qty, price, amount, rate, vat, total`. В «ставку» попадает только целое ≤ 30. Если графы слиплись, количество по стоимости не пересчитывается: стоимость тогда ненадёжна.
- **Сверка** `reconcile(qty, price, amount)`: если кол-во × цена ≠ стоимость (допуск 1%), исправляется то, что даёт «круглый» результат: количество до 3 знаков или цена до 2 знаков. Например, 9,9 → 5,5 (OCR спутал 5 и 9). Если неясно, ничего не трогается.
- Количество потеряно (одиночная цифра на скане часто пропадает), а цена и стоимость есть → количество = стоимость / цена, если получается до 3 знаков.
- Сумма без НДС не указана, но есть «с НДС» и «НДС» → amount = total − vat.
- Единицы: «kt/kr» → кг, «lut/wt» → шт и т.п. (`UNITS`); канонические `кг, г, л, мл, шт` приводятся к одному написанию, остальные («упак», «уп», «пар») остаются как есть.

## Исправление текста OCR (`ocr.fix_lookalikes`)

- Слово, где есть и кириллица, и латиница, переводится в кириллицу (`Caxap` → «Сахар»), но только если в нём есть кириллица или оно целиком из букв-двойников. `Lavazza Crema`, `HB80-280V`, `5W-40` не трогаются.
- Цифры внутри русского слова: 3→з, 0→о, 6→б («3ерНах» → «зернах»). Заглавные посреди слова — в строчные. Числа с единицами («6кг», «1000х5», «0-80мм») не трогаются.

## Реквизиты (`find_requisites`)

- **Номер**: в строке с «накладн» или в следующей — «№ …» либо номер бланка из 6–8 цифр (у ТТН номер напечатан без «№»).
- **Дата**: сначала текстовая «17 июня 2026 г.» (самая надёжная), затем числовая не раньше 2020 года. Строки с «договор», «доверенность», «путевому листу», «основание», «постановление» пропускаются: в них чужие даты и номера.
- **Поставщик**: после «Поставщик/Грузоотправитель/Продавец», если там организация (ООО, ОДО, ЧУП, УП, ИП…; «000» вместо «ООО» тоже), в виде `ООО "Название"` без адреса. Иначе — первая организация в кавычках, которая не получатель, покупатель или плательщик.

## Сопоставление с товарами (`store.match_line`)

1. Точное совпадение ключа `normalize(name)|unit_key(unit)` в `aliases`.
2. Нечёткое совпадение (difflib ≥ 0,85) среди алиасов с той же единицей: скан каждый раз читает название чуть иначе («80мм» и «8Омм»).
3. Угадывание: товар, все значимые слова которого (первые 4 буквы слов длиннее 3) есть в названии строки, при условии что такой товар один. Коэффициент берётся из единиц (`кг → г` = 1000), иначе его задаёт человек.

## Что проверено на реальном скане ТТН (белорусский бланк)

Ошибки распознавания и чем они исправлены:

| Ошибка | Решение |
|---|---|
| Перекос 0,44° | `deskew` |
| Пунктир между строками | удаление тонких полос с разрывами и `_grow` |
| Слившиеся слова шапки | колонки по вертикальным линиям |
| «ТОВАРНЫЙ РАЗДЕЛ» принят за шапку | такие строки исключаются |
| «НОС» вместо «НДС» | исправление в `classify_header` |
| Потерянные однозначные количества | восстановление из стоимости ÷ цену |
| 5,5 прочитано как 9,9 | `reconcile` |
| «120002.4» (слиплись графы) | `parse_cell_numbers` и порог вертикальных линий 175 |
| «3ерНах» | `_fix_russian_word` |

Итог: 8 строк из 8, суммы, НДС и реквизиты сошлись.
