# Распознавание и разноска накладных

Навык собран из рабочей программы CoffeeStock (учёт кофейного автомата). В ней проверено на настоящих сканах ТТН: кривой скан с пунктирными строками распознаётся полностью, итог совпадает до копейки. Код в `scripts/invoice_kit/` не привязан к предметной области: вместо «ингредиентов» в нём «товары» (`items`). Новую программу собирай из него, а не пиши распознавание заново: каждая мелочь здесь лечит реальную ошибку, найденную на сканах.

## Что внутри

| Файл | Что делает |
|---|---|
| `scripts/invoice_kit/recognize.py` | PDF → `Extracted(number, date, supplier, lines=[Line(name, qty, unit, price, vat, total)])`. Сначала текстовый слой и таблицы pdfplumber, затем, для скана, OCR. Шапка таблицы, строки, переносы названий, сверка кол-во × цена = сумма, реквизиты. Без базы данных. |
| `scripts/invoice_kit/ocr.py` | Tesseract (TSV, `rus+eng`, `--psm 11`, 400 dpi): выпрямление скана, удаление линий таблицы и пунктира, поиск вертикальных линий колонок, исправление латиницы и цифр в русских словах. |
| `scripts/invoice_kit/store.py` | SQLite: `items`, `invoices`, `invoice_lines`, `aliases`, `movements`. `match_line` (запомненные сопоставления + нечёткое сравнение ≥ 0,85 + угадывание по словам), `save_extracted` (сам проводит, если всё сопоставлено и есть дата), `save_invoice` (из редактора; перепроводит исправленную), `post/unpost`, `stock`, поиск повторов по хешу и по (номер, дата, поставщик). |
| `scripts/invoice_kit/inbox.py` | Папки `Накладные/Входящие → Обработанные / Ошибки`. Ждёт, пока сканер допишет файл. Повторный файл или повторный скан той же бумаги → «duplicate». |
| `scripts/invoice_kit/editor.py` | Карточка накладной (PySide6): реквизиты, строки, выбор товара, коэффициент, колонка «Приход», «Сохранить и провести». Строки без товара подсвечены жёлтым. |
| `scripts/invoice_kit/cli.py` | `python -m invoice_kit.cli скан.pdf [--json]` — быстро посмотреть, что распознано. |
| `scripts/tests/` | pytest на синтетических PDF: текстовый, скан, «как настоящая» ТТН с перекосом и пунктиром. Запуск: `cd scripts && python -m pytest -q tests`. |
| `references/parsing-notes.md` | Как устроен разбор и какие ошибки сканов чем лечатся. Читай, если накладная распознаётся неверно. |
| `references/windows-build.md` | PyInstaller + встроенный Tesseract, GitHub Actions, автообновление, грабли Windows (кодировки, пути с кириллицей). Читай, когда дело дошло до сборки и раздачи программы. |

Зависимости: `scripts/requirements.txt` (pdfplumber, pypdfium2, numpy, Pillow; PySide6 только для editor; reportlab и pytest для тестов). Для сканов нужен Tesseract с `rus.traineddata`.

## Как строить новую программу

1. **Скопируй пакет** `scripts/invoice_kit/` в проект (например, `myapp/invoice_kit/`), а `scripts/tests/` — в тесты проекта. Прогони тесты: это проверка, что окружение и Tesseract в порядке.
2. **Справочник товаров.** Таблица `items(name, unit, min_stock)`. Единица учёта — в чём считаешь остаток (г, мл, шт, пар, л). Если нужны поля предметной области (артикул, категория, рецептура), добавь свои таблицы рядом и не ломай схему `store.py`: на ней держится разноска.
3. **Обработка папки.** Раз в 10 секунд вызывай `inbox.process_incoming(conn, folders, lambda p: recognize.extract(p, tesseract_path))` в отдельном потоке (QThread): OCR одной страницы занимает несколько секунд. Результаты (`posted / review / error / duplicate`) показывай в журнале.
4. **Проверка человеком.** Накладная со статусом `review` (есть несопоставленные строки или нет даты) открывается в `editor.InvoiceEditor`. Пользователь выбирает товар и коэффициент («1 уп = 50 пар»), услуги и доставку отмечает «Не учитывать». После «Провести» сопоставление запоминается в `aliases`, и следующая такая накладная проводится сама.
5. **Расход.** Продажи и списания — тоже движения в `movements` (`kind='sale'` или `'writeoff'`, количество с минусом). Остаток — `store.stock(conn)`. Инвентаризация — движение `adjust` на разницу между фактом и расчётом.
6. **Отчёты.** Приход по накладным (дата, №, поставщик, наименование, кол-во, цена, НДС, с НДС), оборотная ведомость (на начало, приход, расход, корректировки, на конец), прогноз по среднему расходу.

## Важные решения (почему так)

- **Только локальное распознавание.** Пользователь не хотел отправлять документы в облако: текстовый слой, иначе Tesseract. Не предлагай облачный OCR, пока об этом не попросят.
- **Распознанное ≠ проведённое.** Сама проводится только накладная, где все строки сопоставлены и найдена дата. Остальное ждёт человека. Ошибочный приход хуже, чем лишний клик.
- **Исправление проведённой накладной** удаляет её движения и проводит заново (`save_invoice`), поэтому остатки всегда соответствуют карточке.
- **Повторы.** Тот же файл ловится по SHA-256. Тот же документ, отсканированный ещё раз, — по (номер, дата, поставщик). Без второй проверки приход задваивается.
- **Файл сначала переносится, потом записывается в базу** (имя уже с « (1)», если такое занято). Так у накладной всегда правильная ссылка на PDF.
- **Данные пользователя не попадают в код и в репозиторий.** Настоящие накладные, цены, поставщики, продажи передаются отдельным файлом (например, «Начальные данные.json» рядом с exe) и загружаются в базу. В тестах — только синтетические документы с вымышленными организациями. Перед коммитом проверь grep'ом, что в diff нет реальных названий и номеров.

## Если накладная распознаётся плохо

1. `python -m invoice_kit.cli скан.pdf` — посмотреть строки и реквизиты.
2. Посмотреть, что увидел OCR: `ocr.ocr_pdf(path)[0]` даёт слова с координатами и вертикальные линии; `recognize._group_rows(page.words)` даёт строки.
3. Найти причину по `references/parsing-notes.md`: шапка не найдена, колонки слиплись, латиница вместо кириллицы, точечные линии, чужие даты из договора.
4. Исправление закрепить тестом на синтетическом PDF (`tests/pdf_fixtures.py: make_ttn_scan` — образец), а не подгонкой под один файл.
5. Сервер сборки (Windows) распознаёт чуть иначе, чем Linux. Печать диагностики в тесте (см. `test_skewed_ttn_scan_with_dotted_rows` в CoffeeStock) экономит круги CI.
